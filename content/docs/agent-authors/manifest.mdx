---
title: Agent manifest
description: Define the identity and metadata of an Agent without embedding its executable components.
---

The root manifest is agent.json.

## Minimal manifest

    {
      "$schema": "https://github.com/suissa/agent-behavior-site/blob/main/public/schemas/1.0.0/agent.schema.json",
      "name": "support-agent",
      "version": "1.0.0"
    }

## Metadata

The manifest may also describe:

| Field | Purpose |
| --- | --- |
| name | Stable Agent identifier. |
| version | Agent package version. |
| description | Short purpose statement. |
| author | Package authorship. |
| homepage | Documentation or project homepage. |
| repository | Source repository. |
| license | License identifier. |
| keywords | Discovery metadata. |
| runtime | Runtime compatibility metadata. |
| extensions | Runtime-specific metadata. |

The manifest identifies the Agent but does not inline its behavior.

## Fixed component locations

The runtime discovers components from fixed locations:

| Component | Location |
| --- | --- |
| Agent behavior | SKILL.md |
| Actions | actions/ |
| Knowledge | knowledge/ |
| MCPQ | mcpq.json |

This fixed layout prevents every runtime from inventing a different discovery mechanism.

## Package containment

Every package path MUST resolve inside the Agent root. A manifest that causes package execution or loading to escape that boundary MUST be rejected or isolated according to the applicable component failure rule.

## Versioning

The Agent package version and specification version have different purposes. The specification version defines the package contract. The Agent version identifies a particular Agent release.

Agents SHOULD use Semantic Versioning for the Agent version.
