---
title: Implement an Agent runtime
description: Execute the semantic Agent model while preserving derived Skills, Action boundaries, trajectories, Knowledge, and MCPQ semantics.
---

A conformant runtime treats the Agent as the first-class execution unit.

## Loading sequence

1. Establish the filesystem-resolved Agent root.
2. Locate and validate agent.json.
3. Require and validate the root SKILL.md.
4. Resolve the Agent's semantic identity, Behavior Flow provenance, and Skill provenance when available.
5. Discover Actions from actions/.
6. Discover mcpq.json when present.
7. Initialize authorized Knowledge and evolution facilities.
8. Apply supported extensions.
9. Start execution only after required validation and trust checks pass.

## Semantic execution

The runtime executes:

    Intent
      ↓
    Behavior Flow
      ↓
    Agent Skill
      ↓
    Action selection
      ↓
    Actor
      ↓
    Runtime effects
      ↓
    Trajectory

The portable SKILL.md is not an excuse to erase the Behavior Flow semantics. A runtime that knows the semantic source SHOULD preserve the relationship between the source and its derived Skill.

## Portable versus runtime-owned behavior

Agent Behavior defines:

- Agent identity;
- Agent Skill and its semantic role;
- Action boundaries;
- Knowledge lifecycle boundaries;
- MCPQ configuration;
- failure isolation;
- the distinction between Actor and Runtime.

The runtime decides:

- installation and distribution;
- trust and permissions;
- sandboxing;
- queue implementation;
- scheduling;
- model selection;
- UI;
- observability backend;
- validation implementation.

## Knowledge isolation

Normal execution SHOULD consume only active Skills and Knowledge explicitly authorized by policy.

Raw Evidence and evolution proposals MUST NOT automatically become prompt context.

This preserves the separation between execution, persistent knowledge, and executable behavior demonstrated by WikiSkill.

## Evolution

When evolution is enabled:

    Trajectory
      ↓
    Evidence
      ↓
    Wiki
      ↓
    Proposal
      ↓
    Validation
      ↓
    Behavior Flow
      ↓
    regenerate Agent or Action Skill

The runtime MUST make the validation policy explicit.

A model-generated proposal is not, by itself, evidence of improvement.

Rejected proposals remain retained knowledge and history.

## Trajectory validation

A runtime or attached testing system MAY validate a Trajectory against:

- the triggering Intent;
- selected Behavior Flow path;
- Action inputs;
- Action outputs;
- events;
- state changes;
- errors;
- recovery behavior;
- final outcome.

This allows intent-driven tests to validate semantic outcomes instead of only implementation commands.

## Failure isolation

The runtime SHOULD isolate failures at the narrowest boundary:

- invalid agent.json → reject Agent;
- invalid root SKILL.md → reject Agent;
- invalid Action → disable only that Action;
- invalid MCPQ channel → disable only that channel;
- failed MCP connection → isolate that connection;
- failed queue delivery → apply queue policy;
- failed evolution proposal → preserve active behavior and proposal history.

## Security

Skills, Action scripts, MCP endpoints, queue messages, and learned Knowledge are untrusted inputs until policy authorizes them.

Path containment, secret isolation, sandboxing, authentication, authorization, provenance, correlation, auditability, and policy enforcement are runtime responsibilities.
