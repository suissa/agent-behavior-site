Specification Version: 1.0.0-draft

Status: Working Draft

This document defines the Agent Behavior package model. It is intentionally compatible with the portable portions of Agent Skills and Agent Plugins, while introducing a different semantic center: the Agent is an executable Actor rather than a package of unrelated extensions.

## 1. Status and conformance

The specification uses MUST, MUST NOT, REQUIRED, SHOULD, SHOULD NOT, and MAY as normative terms according to RFC 2119 and RFC 8174.

A conformant runtime MUST implement the package boundary, manifest validation, Agent Skill discovery, Action discovery, and failure isolation rules applicable to the components it supports.

The specification is a working draft. The schemas in this repository are normative only for the corresponding draft revision and MUST NOT be treated as an established industry standard.

## 2. Design lineage

Agent Behavior incorporates four layers of prior work.

### 2.1 Agent Skills

Agent Skills defines a portable directory centered on SKILL.md, with YAML frontmatter and optional scripts, references, and assets. Progressive disclosure allows metadata to be discovered before the full instructions and resources are loaded.

Agent Behavior reuses this file-level contract wherever practical. The semantic role changes: an Agent's SKILL.md describes the Agent's durable behavior, while an Action's SKILL.md describes the behavior required to execute that Action.

### 2.2 Agent Plugins

Agent Plugins 1.0 defines a directory package with a manifest, fixed component locations, Agent Skills, MCP server configuration, extension namespaces, and narrow failure boundaries.

Agent Behavior retains these interoperability principles but changes the package root from a generic Plugin to an Agent. The portable component locations become SKILL.md, actions/, knowledge/, and mcpq.json.

### 2.3 WikiSkill

WikiSkill demonstrates a three-layer learning architecture: raw execution experience, a persistent knowledge wiki, and executable skills. Its evolution loop uses experience to propose skill changes and keeps a candidate only when an objective validation score strictly improves.

Agent Behavior adopts this separation as a first-class knowledge lifecycle. A runtime MUST NOT silently turn raw experience into active behavior. Promotion MUST pass the configured validation policy.

### 2.4 MCP and asynchronous execution

MCP supplies interoperable tool and resource communication. Modern MCP work also provides durable task primitives for long-running operations.

Agent Behavior introduces MCPQ as the Agent-level channel abstraction. Its default channel mode is a Queue, because Agent execution is not inherently a request/response interaction.

## 3. Terminology

| Term | Meaning |
| --- | --- |
| Agent | Executable Actor described by an Agent package. |
| Agent Skill | Behavioral SKILL.md attached to an Agent. |
| Action | A named executable capability of an Agent, represented by an Action directory and its SKILL.md. |
| Knowledge | Persistent evidence, wiki knowledge, proposals, and evolution state. |
| MCPQ | Agent communication channel abstraction combining queue-oriented delivery with optional MCP interoperability. |
| Queue | Default MCPQ channel mode for asynchronous Agent communication. |
| Runtime | Host that discovers, validates, loads, executes, and isolates Agents. |
| Evidence | Immutable or append-only execution observations used by the knowledge lifecycle. |
| Wiki | Persistent, curated knowledge derived from evidence. |
| Proposal | Candidate change to an Agent Skill or Action Skill. |
| Validation gate | Objective or policy-controlled test that decides whether a proposal may become active. |
| Actor | Runtime identity responsible for executing an Agent. |

## 4. Agent package model

An Agent is a filesystem package rooted at one directory.

A complete package MAY contain:

    agent-name/
    ├── agent.json                 # REQUIRED
    ├── SKILL.md                   # REQUIRED
    ├── actions/                   # OPTIONAL
    │   └── action-name/
    │       ├── SKILL.md           # REQUIRED for each Action
    │       ├── scripts/           # OPTIONAL
    │       ├── references/        # OPTIONAL
    │       └── assets/            # OPTIONAL
    ├── knowledge/                 # OPTIONAL
    │   ├── evidence/
    │   ├── wiki/
    │   └── evolution/
    ├── mcpq.json                  # OPTIONAL
    ├── LICENSE
    └── CHANGELOG.md

The runtime MUST resolve package paths within the filesystem-resolved Agent root. Symlinks, junctions, and equivalent mechanisms MUST NOT allow package configuration to escape the Agent root.

The Agent root is the trust and discovery boundary. Runtime sandboxing is a separate concern and is not implied by this filesystem rule.

## 5. Manifest

The root manifest MUST be agent.json.

It MUST be a JSON object containing:

- $schema
- name
- version

It MAY additionally contain description, author, homepage, repository, license, keywords, runtime, extensions, and other fields explicitly standardized by a future specification revision.

Unknown top-level fields SHOULD be reported and ignored when the manifest is otherwise valid. A malformed required field is fatal to the Agent package.

Example:

    {
      "$schema": "https://github.com/suissa/agent-behavior-site/blob/main/public/schemas/1.0.0/agent.schema.json",
      "name": "sales-agent",
      "version": "1.0.0",
      "description": "Handles order creation and customer follow-up."
    }

The manifest identifies the Agent. It MUST NOT inline the Agent Skill, Action definitions, or MCPQ configuration. Those components have fixed locations.

## 6. Agent Skill

The root SKILL.md is REQUIRED.

It follows the Agent Skills file mechanics:

    ---
    name: sales-agent
    description: Handles sales interactions, validates order intent, and recovers safely from incomplete information.
    ---

    # Sales Agent

    Describe the durable behavior of the Agent.

The name and description fields retain the portability constraints of Agent Skills. The body defines the Agent's behavioral contract.

The Agent Skill SHOULD describe:

- intent and scope;
- evidence the Agent should inspect;
- decisions and invariants;
- execution principles;
- recovery behavior;
- important failure modes;
- escalation and human-healing boundaries.

An Agent Skill is not merely a prompt file. It is the durable behavioral definition from which runtime instructions, evaluations, documentation, and future Action behavior may be derived.

## 7. Actions

Actions are the executable capabilities of an Agent.

The fixed location is actions/. Each immediate child directory containing a valid SKILL.md is one Action.

Example:

    actions/
    ├── create-order/
    │   ├── SKILL.md
    │   └── references/
    │       └── order-contract.md
    └── cancel-order/
        └── SKILL.md

An Action Skill uses the same portable SKILL.md mechanics as Agent Skills, but its semantics are scoped to one executable capability.

An Action SHOULD specify:

1. when the Action applies;
2. required evidence and inputs;
3. preconditions and invariants;
4. decision logic;
5. execution steps;
6. postconditions and observable outputs;
7. recovery and escalation;
8. prohibited or unsafe outcomes.

Actions MAY use scripts, references, and assets following Agent Skills conventions.

A runtime MUST NOT infer an Action merely from arbitrary files outside actions/.

## 8. Knowledge and evolution

Knowledge is intentionally separate from active Skills.

A recommended layout is:

    knowledge/
    ├── evidence/
    │   └── <execution>.jsonl
    ├── wiki/
    │   ├── index.md
    │   ├── patterns/
    │   └── log.md
    └── evolution/
        ├── proposals/
        ├── validations/
        └── decisions/

### 8.1 Evidence

Evidence records what happened during execution. It SHOULD be append-only and SHOULD contain enough provenance to reconstruct the observation without exposing secrets or unnecessary personal data.

### 8.2 Wiki

The Wiki is persistent knowledge distilled from evidence: successful strategies, failure modes, root causes, constraints, counterexamples, and reusable patterns.

The Wiki MUST NOT be treated as automatically active runtime instructions.

### 8.3 Evolution

A proposer MAY derive a candidate change to an Agent Skill or Action Skill from the Wiki and evidence.

A candidate MUST be evaluated by the configured validation policy before activation when validation is required by the Agent manifest or runtime policy.

The default promotion rule is:

    candidate_score > best_score
            => promote
    otherwise
            => reject active change
            + retain evidence and proposal history

A rejected proposal MUST NOT erase the knowledge that led to it. This preserves the central WikiSkill property that knowledge compounds even when a particular skill change does not.

## 9. MCPQ channels

MCPQ is the communication abstraction of an Agent.

The root configuration is mcpq.json.

A channel has a stable name and a mode. The default mode is queue.

    {
      "$schema": "https://github.com/suissa/agent-behavior-site/blob/main/public/schemas/1.0.0/mcpq.schema.json",
      "channels": {
        "orders": {
          "type": "queue",
          "delivery": "at-least-once"
        },
        "human-healing": {
          "type": "queue"
        }
      }
    }

Queue mode is the default because an Agent is an asynchronous Actor: work can be accepted, retried, delayed, resumed, routed, or escalated without requiring the caller to keep a request open.

MCP mode MAY be used where interoperability with an MCP server is required. The MCP protocol remains authoritative for MCP message and capability semantics.

MCPQ does not redefine MCP. It defines where an Agent communicates and how work is delivered at the Agent boundary.

### 9.1 Queue semantics

A Queue channel SHOULD define:

- delivery semantics;
- ordering requirements when relevant;
- retry policy;
- visibility or lease behavior;
- dead-letter behavior;
- correlation and causation identifiers;
- idempotency requirements;
- acknowledgement semantics.

The exact queue technology is runtime-defined.

### 9.2 MCP interoperability

An MCPQ channel MAY expose or consume MCP operations. A runtime MUST NOT assume that an MCP endpoint is synchronous simply because MCP is being used.

Long-running work MAY use MCP Tasks or an equivalent queue-backed runtime mechanism. MCP's current Tasks extension models durable asynchronous execution and deferred result retrieval. The Agent Behavior runtime may map that capability onto a Queue without changing MCP wire semantics.

## 10. Discovery

A conformant runtime MUST:

1. establish the filesystem-resolved Agent root;
2. load and validate agent.json;
3. load the root SKILL.md;
4. discover immediate Action directories;
5. discover mcpq.json when present;
6. initialize supported knowledge and evolution facilities according to policy;
7. report independent failures without invalidating unrelated valid components.

Missing optional component locations are valid absence.

A malformed root manifest or missing root SKILL.md invalidates the Agent package.

A malformed Action invalidates only that Action.

A malformed MCPQ channel invalidates only that channel when it can be isolated safely.

A runtime MUST NOT make a broken Action or channel prevent independent Actions or channels from loading.

## 11. Progressive disclosure

Agent Behavior retains the progressive-disclosure principle of Agent Skills.

At discovery time, runtimes SHOULD load only lightweight metadata.

When an Action is selected, the runtime loads its complete SKILL.md.

References, assets, and scripts SHOULD be loaded or executed only when required by the Action.

The root Agent Skill may be loaded earlier because it defines the Agent's behavior, but runtimes SHOULD still avoid loading unrelated Action resources into context.

## 12. Security and trust

Skills and Actions can change Agent behavior and may execute scripts. A valid package is therefore not automatically trusted.

Runtimes SHOULD provide:

- package provenance;
- content digests or signatures where available;
- explicit permission and trust policy;
- sandboxing for subprocesses;
- secret isolation;
- path containment;
- audit logs;
- policy enforcement before external side effects.

MCPQ channels MUST preserve authentication, authorization, tenant isolation, and correlation boundaries.

Knowledge ingestion SHOULD sanitize secrets and sensitive data before persistence. The Agent Behavior specification does not grant a Skill permission to read arbitrary private knowledge.

## 13. Compatibility with Agent Skills

A directory containing a conventional Agent Skills SKILL.md can be represented as an Action without changing the file itself.

This makes migration possible:

    Agent Skill
        │
        ├── SKILL.md
        ├── scripts/
        ├── references/
        └── assets/
                 │
                 ▼
    Agent Behavior Action
        actions/<name>/
        ├── SKILL.md
        ├── scripts/
        ├── references/
        └── assets/

The difference is semantic scope. Agent Skills says "this is reusable expertise for an agent"; Agent Behavior says "this is the behavior and executable capability of this Action within an Agent".

## 14. Compatibility with Agent Plugins

An Agent Plugin can be adapted mechanically:

    plugin.json       → agent.json
    skills/<name>/    → actions/<name>/
    mcp.json          → mcpq.json

The Agent Behavior model adds the root SKILL.md and optional knowledge/ lifecycle.

A compatibility layer MAY expose Agent Behavior packages as Agent Plugins by projecting Actions as Skills and MCPQ MCP bindings as MCP servers.

This projection is intentionally lossy when the target format has no representation for Agent identity, queue semantics, or persistent knowledge.

## 15. Compatibility with WikiSkill

WikiSkill's separation between experience, persistent knowledge, and executable skills maps directly:

| WikiSkill concept | Agent Behavior |
| --- | --- |
| Raw execution traces | knowledge/evidence/ |
| Wiki | knowledge/wiki/ |
| Active skills | Agent SKILL.md and Action SKILL.md |
| Skill proposer | Evolution subsystem |
| Validation gate | Agent validation policy |
| Rejected proposal retained | knowledge/evolution/ |

Agent Behavior does not require a particular LLM, proposer architecture, validator implementation, or benchmark. The lifecycle is the portable contract; the implementation is runtime-specific.

## 16. Versioning

The specification version identifies the manifest and channel schemas together.

Published schema identifiers MUST remain immutable.

Agents SHOULD use Semantic Versioning for version.

A breaking change to the Agent package contract requires a new specification version.

An Action MAY evolve independently when its behavior contract is versioned by the containing Agent package or an explicit Action version policy.

## 17. Conformance checklist

A runtime claiming conformance MUST:

- validate the Agent root boundary;
- validate agent.json;
- require and load the root SKILL.md;
- discover Actions from actions/;
- preserve Agent Skills-compatible SKILL.md semantics;
- isolate invalid Actions;
- recognize mcpq.json when MCPQ is supported;
- use Queue as the default MCPQ mode;
- isolate invalid channels;
- keep persistent knowledge separate from active runtime behavior;
- preserve rejected evolution proposals when an evolution subsystem is enabled;
- enforce configured validation gates before promoting learned behavior;
- avoid treating external Agent Skill, Plugin, MCP, or WikiSkill implementations as trusted merely because they are structurally valid.
