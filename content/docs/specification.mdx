Specification Version: 1.0.0-draft

Status: Working Draft

This document defines the Agent Behavior package and execution model. It reuses portable portions of Agent Skills and Agent Plugins, incorporates the persistent-knowledge and gated-evolution ideas demonstrated by WikiSkill, and adds a semantic execution model centered on Agent, Behavior Flow, Action, Actor, Runtime, and MCPQ.

The key semantic rule is:

> Every semantic Agent instance has one Agent Skill derived from its Behavior Flow.

The SKILL.md file is therefore a portable behavioral projection of the semantic model. It is not the ultimate semantic source of truth.

## 1. Status and conformance

The specification uses MUST, MUST NOT, REQUIRED, SHOULD, SHOULD NOT, and MAY as normative terms according to RFC 2119 and RFC 8174.

A conformant runtime MUST implement package-boundary validation, Agent identity discovery, Agent Skill discovery, Action discovery, and the failure-isolation rules applicable to the components it supports.

This is a working draft. The schemas and canonical identifiers in this repository are draft artifacts and MUST NOT be presented as an established industry standard.

## 2. Design lineage

Agent Behavior is cumulative, but its semantics are intentionally different from the projects it incorporates.

### 2.1 Agent Skills

Agent Skills standardizes a portable directory centered on SKILL.md, with YAML frontmatter and optional scripts, references, and assets. Its progressive-disclosure model lets a runtime discover lightweight metadata before loading the complete instructions and supporting resources.

Agent Behavior reuses those file mechanics. The semantic role is extended:

- root SKILL.md is the Agent's durable behavioral projection;
- Action SKILL.md is the behavioral projection of one executable capability;
- scripts, references, and assets remain implementation resources.

The current Agent Skills specification requires name and description in SKILL.md frontmatter, constrains names to lowercase letters, numbers, and hyphens, and supports optional license, compatibility, metadata, and allowed-tools fields. See the [Agent Skills specification](https://github.com/agentskills/agentskills/blob/main/docs/specification.mdx).

### 2.2 Agent Plugins

Agent Plugins 1.0 standardizes a package with plugin.json, fixed component locations, Skills, MCP servers, extensions, and narrow failure boundaries. It is explicitly a package format for reusable components rather than an Agent execution ontology. See the [Agent Plugins 1.0 specification](https://github.com/agentplugins/agent-plugins-spec/blob/main/spec/1.0.0.md).

Agent Behavior keeps the useful packaging and isolation principles while changing the semantic center from Plugin to Agent.

### 2.3 WikiSkill

WikiSkill separates raw execution experience, persistent knowledge, and executable skills, then uses a proposal and validation process to evolve skills. The paper explicitly identifies persistent knowledge accumulation as important to skill evolution. See [WikiSkill](https://arxiv.org/abs/2608.27454).

Agent Behavior maps that lifecycle into evidence, Wiki, evolution proposals, validation, and active derived Skills.

### 2.4 MCP and asynchronous execution

MCP defines interoperable protocol semantics. In 2026, the official Tasks extension provides durable task handles for long-running work, deferred result retrieval, progress state, cancellation, and input-required flows. See the [MCP Tasks extension](https://github.com/modelcontextprotocol/ext-tasks) and [SEP-2663](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/seps/2663-tasks-extension.md).

Agent Behavior introduces MCPQ as the Agent-level communication boundary. Queue is the default execution mode; MCP is an interoperability binding, not a replacement for queue semantics.

## 3. Semantic model

Agent Behavior separates semantic definition, behavioral projection, executable capability, execution identity, and execution environment.

### 3.1 A3 execution ontology

The core chain is:

    AtomicSkill
         ↓
    AtomicBehavior
         ↓
       Action
         ↓
       Actor
         ↓
      Runtime

Each level has a different responsibility.

| Level | Meaning |
| --- | --- |
| AtomicSkill | Smallest reusable semantic unit of capability, knowledge, or decision logic. |
| AtomicBehavior | Smallest behavior-level unit that composes one or more AtomicSkills into an observable semantic behavior. |
| Action | Executable capability boundary exposed by an Agent. |
| Actor | Concrete execution identity that performs the Agent behavior. |
| Runtime | Host that schedules, isolates, authorizes, observes, and executes Actors. |

This distinction prevents a Markdown Skill, an executable Action, and a runtime identity from being treated as the same object.

### 3.2 Intent

Intent is the semantic request, goal, or event meaning that causes an Agent behavior path to become relevant.

An Intent is not an implementation command. It describes what should be achieved or what meaningful condition occurred.

A runtime MAY receive an Intent directly from a user, another Agent, an event, a scheduled trigger, or an external system.

### 3.3 Behavior Flow

A Behavior Flow is the semantic flow that connects Intent, behaviors, Actions, decisions, outcomes, and recovery.

It is the source model from which the portable Agent Skill is derived.

Conceptually:

    Intent
      ↓
    Behavior Flow
      ├── AtomicBehavior
      │      └── AtomicSkill
      ├── decision / invariant
      ├── Action
      ├── recovery / escalation
      └── Outcome
             ↓
        Agent SKILL.md
        (derived projection)

A conformant implementation MUST preserve the semantic identity between the Agent Skill and the Behavior Flow from which it was derived.

The specification does not force one DSL for Behavior Flow. A project MAY represent it as structured JSON, YAML, semantic Markdown, another formal DSL, or generated artifacts, provided the implementation preserves identity, ordering or transition semantics, inputs, outputs, invariants, and outcomes.

### 3.4 Trajectory

A Trajectory is the observed execution path through a Behavior Flow.

The distinction is:

    Behavior Flow = what should happen
    Trajectory   = what did happen

Trajectories are evidence. They MUST NOT silently become active behavior.

This distinction provides the bridge to intent-driven testing, trajectory validation, observability, and experience-driven evolution.

### 3.5 Agent

An Agent is a first-class semantic execution unit and Actor definition.

An Agent MUST have:

- stable identity in agent.json;
- one root Agent Skill;
- zero or more Actions;
- optional persistent Knowledge;
- optional MCPQ channels.

The Agent Skill is derived from its Behavior Flow and expresses the durable behavior required of the Agent as a whole.

## 4. Package model

An Agent is a filesystem package rooted at one directory.

A complete package MAY contain:

    agent-name/
    ├── agent.json                 # REQUIRED
    ├── SKILL.md                   # REQUIRED
    ├── actions/                   # OPTIONAL
    │   └── action-name/
    │       ├── SKILL.md           # REQUIRED for each Action
    │       ├── scripts/           # OPTIONAL
    │       ├── references/        # OPTIONAL
    │       └── assets/            # OPTIONAL
    ├── knowledge/                 # OPTIONAL
    │   ├── evidence/
    │   ├── wiki/
    │   └── evolution/
    ├── mcpq.json                  # OPTIONAL
    ├── LICENSE
    └── CHANGELOG.md

The runtime MUST resolve package paths within the filesystem-resolved Agent root. Symlinks, junctions, and equivalent mechanisms MUST NOT allow package configuration to escape the Agent root.

The Agent root is the discovery and containment boundary. Sandbox isolation is a separate runtime responsibility.

## 5. Manifest

The root manifest MUST be agent.json.

It MUST be a JSON object containing:

- $schema;
- name;
- version.

It MAY additionally contain description, author, homepage, repository, license, keywords, runtime, and extensions.

The manifest identifies the Agent. It MUST NOT inline the Agent Skill, Action definitions, Knowledge, or MCPQ configuration. These components have separate, fixed locations.

The draft schema is deliberately closed: extension data belongs under extensions rather than arbitrary top-level keys.

## 6. Agent Skill

The root SKILL.md is REQUIRED and MUST contain YAML frontmatter followed by Markdown. Its frontmatter name MUST equal agent.json name.

At minimum:

    ---
    name: sales-agent
    description: Handles sales interactions, validates order intent, and recovers safely from incomplete information.
    ---

    # Sales Agent

    Durable Agent behavior derived from the Agent Behavior Flow.

The file follows the portable Agent Skills mechanics while taking a different semantic role.

The Agent Skill SHOULD describe:

- Agent intent and scope;
- evidence and context that should be inspected;
- decisions and invariants;
- execution principles;
- recovery behavior;
- important failure modes;
- escalation and human-healing boundaries;
- expected outcomes.

The root SKILL.md is a projection. A semantic source MAY regenerate it. Implementations MUST NOT create contradictory active behavior by silently editing the derived Skill independently of its semantic source.

### 6.1 Progressive disclosure

At discovery time, a runtime SHOULD load lightweight Skill metadata.

When an Action is selected, its complete SKILL.md SHOULD be loaded.

References, assets, and scripts SHOULD be loaded only when required.

This preserves the context-efficiency principle of Agent Skills. See the [Agent Skills specification](https://github.com/agentskills/agentskills/blob/main/docs/specification.mdx).

## 7. Actions

Actions are the executable capability boundaries of an Agent.

The fixed location is actions/. Each immediate child directory containing a valid SKILL.md is one Action.

    actions/
    ├── create-order/
    │   ├── SKILL.md
    │   └── references/
    │       └── order-contract.md
    └── cancel-order/
        └── SKILL.md

An Action Skill is the portable behavioral projection for one Action. Its frontmatter name MUST equal the Action directory name.

An Action SHOULD specify:

1. applicability or trigger;
2. required evidence and inputs;
3. preconditions and invariants;
4. decision logic;
5. execution semantics;
6. postconditions and observable outputs;
7. recovery and escalation;
8. prohibited or unsafe outcomes.

Actions MAY use scripts, references, and assets following Agent Skills conventions.

A runtime MUST NOT infer an Action from arbitrary files outside actions/.

An Action belongs to exactly one Agent package. Reusable expertise can be shared as an external Skill and then adapted into an Agent Action without changing the underlying SKILL.md mechanics.

## 8. Knowledge

Knowledge is separate from active behavioral instructions.

Recommended layout:

    knowledge/
    ├── evidence/
    │   └── <trajectory>.jsonl
    ├── wiki/
    │   ├── index.md
    │   ├── patterns/
    │   └── log.md
    └── evolution/
        ├── proposals/
        ├── validations/
        └── decisions/

### 8.1 Evidence

Evidence records what happened during execution. It SHOULD be append-only and contain provenance sufficient to reconstruct the observation without persisting secrets or unnecessary personal data.

Evidence may include validated Trajectories, outcomes, failures, metrics, traces, events, and other runtime observations.

### 8.2 Wiki

The Wiki is persistent knowledge distilled from Evidence.

It can contain:

- successful strategies;
- failure modes;
- root causes;
- constraints;
- counterexamples;
- reusable patterns.

The Wiki MUST NOT be treated as automatically active runtime instructions.

### 8.3 Evolution

An evolution subsystem MAY use Evidence and Wiki knowledge to propose changes to a Behavior Flow, Agent Skill projection, or Action behavior.

The preferred direction is:

    Evidence
      ↓
    Wiki
      ↓
    Proposal
      ↓
    Validation
      ↓
    Behavior Flow change
      ↓
    Derived Skill regeneration

A candidate MUST pass the configured validation policy before becoming active when validation is required.

A rejected proposal MUST NOT erase the Evidence, Wiki knowledge, or proposal history that produced it.

This preserves the central WikiSkill principle that knowledge can compound even when a particular behavior change is rejected. See [WikiSkill](https://arxiv.org/abs/2608.27454).

## 9. MCPQ

MCPQ is the communication boundary of an Agent.

The root configuration is mcpq.json.

A channel has a stable name and a type. The default type is queue.

    {
      "$schema": "https://github.com/suissa/agent-behavior-site/blob/main/public/schemas/1.0.0/mcpq.schema.json",
      "channels": {
        "orders": {
          "type": "queue",
          "delivery": "at-least-once"
        },
        "human-healing": {
          "type": "queue"
        }
      }
    }

Queue is the default because an Agent Actor may need to accept work, retry, delay, resume, fan out, wait for human healing, or hand work to another Actor without keeping the initiating connection open.

### 9.1 Queue semantics

A Queue channel SHOULD define the guarantees that matter to the Actor:

- delivery semantics;
- ordering requirements when relevant;
- retry policy;
- acknowledgement semantics;
- visibility or lease behavior;
- dead-letter behavior;
- correlation and causation identifiers;
- idempotency requirements;
- cancellation or expiry semantics when supported.

The queue technology is runtime-defined.

A runtime MUST NOT advertise guarantees it cannot enforce.

### 9.2 MCP interoperability

An MCPQ channel MAY bind an Agent boundary to MCP.

MCP remains authoritative for:

- MCP message semantics;
- capability negotiation;
- authorization;
- transports;
- MCP lifecycle;
- MCP Tasks semantics.

MCPQ does not redefine MCP.

### 9.3 MCP Tasks

Current MCP Tasks is an official extension identified as io.modelcontextprotocol/tasks. It models durable asynchronous task state with polling and deferred results. See the [MCP Tasks extension](https://github.com/modelcontextprotocol/ext-tasks) and [SEP-2663](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/seps/2663-tasks-extension.md).

An Agent Behavior runtime MAY implement an MCP channel using an internal Queue. That mapping is an implementation strategy, not a change to the MCP wire protocol.

## 10. Actor and Runtime

The Agent describes behavior; the Actor is the execution identity; the Runtime provides the environment in which execution occurs.

    Semantic Agent
         │
         ▼
    Agent Skill
         │
         ▼
       Actor
         │
         ▼
      Runtime
       ├── scheduling
       ├── isolation
       ├── authorization
       ├── observability
       └── policy

A runtime is responsible for operational concerns that should not be hidden inside SKILL.md, including sandboxing, secret handling, process management, model selection, queue implementation, and observability backends.

An Agent package MUST NOT assume that the runtime is a single process.

## 11. Discovery and failure isolation

A conformant runtime MUST:

1. establish the filesystem-resolved Agent root;
2. load and validate agent.json;
3. load the root SKILL.md;
4. resolve the Agent's semantic identity, Behavior Flow provenance, and Skill provenance when available;
5. discover immediate Action directories;
6. discover mcpq.json when present;
7. initialize authorized Knowledge facilities;
8. apply supported extensions;
9. start execution only after required validation and trust checks pass.

Failure boundaries are narrow:

| Failure | Effect |
| --- | --- |
| Invalid agent.json | Reject Agent. |
| Missing or invalid root SKILL.md | Reject Agent. |
| Invalid Action | Disable only that Action. |
| Invalid MCPQ channel | Disable only that channel when safely isolatable. |
| MCP connection failure | Disable only that connection unless explicitly required by Agent policy. |
| Queue delivery failure | Apply queue retry or dead-letter policy. |
| Failed evolution proposal | Keep current active behavior and retain proposal history. |

A broken component MUST NOT disable independent valid components.

## 12. Intent, trajectory, testing, and observability

Agent Behavior treats execution as a semantic trajectory rather than only a sequence of log lines.

Conceptually:

    Intent
      ↓
    Behavior Flow
      ↓
    Atomic Behaviors
      ↓
    Actions
      ↓
    Observed Trajectory
      ↓
    Evidence
      ↓
    Validation / Knowledge

This permits a runtime or testing system to ask whether the observed Trajectory satisfied the intended Behavior Flow, including payloads, events, writes, reads, outcomes, and recovery behavior.

Intent-driven tests MAY express desired outcomes such as "I HOPE SEE Dashboard" rather than imperative implementation steps. A representative trajectory language can express an actor and intent context such as AS Human, followed by interactions and a desired outcome. The syntax of such tests is outside this package format, but the semantic distinction is relevant: a test wish validates the Trajectory against the Behavior Flow instead of merely checking an implementation command.

Observability systems MAY project events, metrics, traces, states, errors, and trajectories into Evidence. Such telemetry MUST remain subject to privacy, security, and retention policy.

## 13. Security and trust

Structural validity is not trust.

Skills, Action scripts, MCP endpoints, queue messages, and learned Knowledge MUST be treated as untrusted until runtime policy authorizes them.

Runtimes SHOULD provide:

- package provenance;
- content digests or signatures where available;
- explicit trust and permission policy;
- path containment;
- subprocess sandboxing;
- secret isolation;
- authentication and authorization;
- tenant isolation;
- auditability;
- policy enforcement before external side effects.

Knowledge ingestion SHOULD sanitize secrets and unnecessary personal data before persistence.

MCPQ MUST preserve authorization and correlation boundaries across asynchronous delivery.

A human-healing channel MUST carry sufficient correlation and authorization context to allow safe continuation of the original Behavior Flow without transferring unnecessary secrets.

## 14. Semantic source versus portable artifacts

The specification distinguishes semantic source artifacts from portable runtime projections.

The semantic source MAY describe:

- Intent;
- Behavior Flow;
- AtomicSkills;
- AtomicBehaviors;
- Actions;
- invariants;
- outcomes;
- runtime policies.

The portable package contains executable and discoverable projections:

    Behavior Flow
        │
        ├──→ Agent SKILL.md
        │
        └──→ Action SKILL.md files
                    │
                    ├──→ scripts/
                    ├──→ references/
                    └──→ assets/

This allows Semantic-as-Code implementations to use structured semantic files without making a specific authoring DSL part of the portable package contract.

The important invariant is traceability: a runtime-visible Skill MUST be attributable to a semantic definition and version.

## 15. Compatibility with Agent Skills

A conventional Agent Skills directory can be adapted into an Action:

    External Skill
        │
        ├── SKILL.md
        ├── scripts/
        ├── references/
        └── assets/
                 │
                 ▼
    Agent Behavior Action
        actions/<name>/
        ├── SKILL.md
        ├── scripts/
        ├── references/
        └── assets/

The file-level mechanics remain portable; the semantic owner changes from reusable expertise to capability belonging to this Agent.

The reverse projection is also possible: an Action Skill can be exposed as a conventional Agent Skill when the hosting environment does not understand Agent Behavior.

## 16. Compatibility with Agent Plugins

An Agent Plugin can be projected conceptually:

    plugin.json        → agent.json
    skills/<name>/     → actions/<name>/
    mcp.json           → mcpq.json

The projection is intentionally not lossless.

Agent Behavior adds:

- an Agent as the semantic execution unit;
- a root Agent Skill;
- Behavior Flow derivation;
- Action ownership;
- persistent Evidence and Wiki knowledge;
- gated evolution;
- Queue-first MCPQ communication;
- Actor and Runtime separation.

A compatibility layer MAY expose Actions as Plugin Skills and MCPQ MCP bindings as Plugin MCP servers.

A plugin package remains valid as a plugin even though it does not contain these additional semantic layers. Agent Behavior MUST NOT claim that every Plugin runtime supports them.

## 17. Compatibility with WikiSkill

WikiSkill's separation maps as follows:

| WikiSkill | Agent Behavior |
| --- | --- |
| Raw execution experience | knowledge/evidence/ |
| Persistent wiki | knowledge/wiki/ |
| Executable skill | derived Agent or Action SKILL.md |
| Skill proposer | evolution subsystem |
| Validation gate | configured Agent or Runtime validation policy |
| Rejected proposal retained | knowledge/evolution/ |

The principal semantic difference is that Agent Behavior places the Behavior Flow before the portable Skill projection. A learning subsystem SHOULD therefore propose semantic behavior changes first and regenerate the Skill projection rather than treating arbitrary prompt text as the sole source of truth.

## 18. Scope boundaries

Agent Behavior is an Agent execution and package specification, not a specification for an entire application stack.

The following may integrate with Agent Behavior but are outside this package contract unless another specification is adopted:

- A2UI or a particular frontend protocol;
- a specific database or storage-agent topology;
- a specific observability backend;
- a particular LLM or multi-agent framework;
- a particular queue implementation;
- application-level LGPD data models;
- a particular AON implementation.

This boundary prevents unrelated infrastructure choices from becoming accidental parts of the portable Agent format.

## 19. Versioning

The specification version identifies the package contract and its canonical schemas together.

Draft schema identifiers are provisional. Once a release is published, its canonical schema identifiers MUST be immutable and MUST NOT be reassigned to different contents.

Agent packages SHOULD use Semantic Versioning for version.

A breaking change to the Agent package contract requires a new specification version.

Action behavior MAY evolve independently when the containing Agent version or an explicit Action version policy establishes the compatibility boundary.

## 20. Conformance checklist

A runtime claiming conformance MUST:

- validate the Agent root boundary;
- validate agent.json;
- require and load the root Agent Skill;
- preserve the Agent Skill to Behavior Flow semantic derivation;
- discover Actions only from actions/;
- preserve Agent Skills-compatible SKILL.md mechanics;
- isolate invalid Actions;
- recognize mcpq.json when MCPQ is supported;
- default channel type to queue when omitted;
- isolate invalid MCPQ channels;
- keep Knowledge separate from active runtime behavior;
- preserve rejected evolution proposals when evolution is enabled;
- enforce validation gates before promoting learned behavior;
- preserve correlation, authorization, and identity across asynchronous work;
- avoid treating structurally valid external Skills, Plugins, MCP endpoints, or Wiki artifacts as automatically trusted.
