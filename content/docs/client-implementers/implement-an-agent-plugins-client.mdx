---
title: Implement an Agent runtime
description: Add Agent Behavior discovery, validation, execution, knowledge, and MCPQ support to a runtime.
---

A conformant runtime treats the Agent as the primary execution unit.

## Loading sequence

1. Establish the filesystem-resolved Agent root.
2. Locate and validate agent.json.
3. Require and validate the root SKILL.md.
4. Discover Actions from actions/.
5. Discover mcpq.json when present.
6. Initialize knowledge and evolution facilities according to runtime policy.
7. Apply extensions owned by the runtime.
8. Start execution only after required validation and trust checks pass.

## Portable versus runtime-owned behavior

Agent Behavior defines:

- package structure;
- Agent identity;
- Agent and Action Skill semantics;
- Action discovery;
- knowledge lifecycle boundaries;
- MCPQ channel configuration;
- failure isolation.

A runtime decides:

- installation and distribution;
- trust and permissions;
- sandboxing;
- queue implementation;
- process scheduling;
- model selection;
- UI;
- observability backend;
- validation implementation.

## Execution model

The runtime should maintain an explicit boundary:

    User or Event
          |
          v
       Agent Actor
          |
       +--+--+
       |     |
       v     v
    Action  MCPQ
       |     |
       +--+--+
          |
       Runtime

The root Agent Skill supplies durable behavior. The selected Action supplies capability-specific behavior. MCPQ supplies the communication boundary.

## Knowledge isolation

Normal execution SHOULD consume only the approved active Skills and the knowledge explicitly authorized by runtime policy.

The raw evidence store and the evolution Wiki should not automatically become prompt context. This preserves the separation demonstrated by WikiSkill between task execution and the subsystem that learns from execution.

## Evolution

If the runtime supports evolution:

1. collect execution evidence;
2. consolidate evidence into persistent Wiki knowledge;
3. generate a candidate Skill or Action change;
4. validate it on representative held-out work;
5. promote only when the configured gate passes;
6. retain rejected proposals and their evidence.

The runtime MUST make the validation policy explicit. A model-generated proposal is not, by itself, evidence that the proposal improved behavior.

## Failure isolation

The runtime SHOULD isolate failures at the narrowest possible boundary:

- invalid agent.json → reject Agent;
- invalid root SKILL.md → reject Agent;
- invalid Action → disable that Action;
- invalid MCPQ channel → disable that channel;
- failed MCP connection → disable that connection;
- failed queue delivery → apply the queue retry policy;
- failed learned proposal → keep the current active behavior and retain the proposal history.

## Security

A runtime should treat Skills, Action scripts, MCP endpoints, queue messages, and learned knowledge as untrusted inputs until policy says otherwise.

Path containment, secret isolation, sandboxing, authorization, provenance, and auditability are runtime responsibilities.
